# M15 规则投递形态效率对比报告（P3）

> 目的：为「工作日志标准化」（M15）**定稿默认的规则投递形态**，并记录一次真实数据下的实测基线。
> 方法：`backend/daily_form_bench.py`（可复跑）在真实 Agent 日志上对三种形态做同批对比。
> 关联文档：[MEMORY-DAILY-STANDARDIZER-PLAN.md](MEMORY-DAILY-STANDARDIZER-PLAN.md)（方案与运维手册附录 E）、
> [DEVELOPMENT.md](DEVELOPMENT.md)（模块 M15）。
> 实测环境：MiniMax `MiniMax-M2.7-highspeed`（OpenAI 兼容协议，`temperature=0.3`，`max_tokens=4096`），
> 2026-09-24，27 次真实调用 / 132,238 tokens。

---

## 一、结论摘要

1. **默认形态定稿为 ③ `system_embedded`（规则全文进 system prompt）**。
   在三天的样本上，它**每一项指标都不劣于**另外两种形态，且在三个可决策维度上同时胜出：
   输出 token −9.7%（1551 → 1400）、单日耗时 −13.3%（26.6s → 23.1s）、
   三次重复的输出一致性最高（相似度 0.442 → 0.518）、强规则通过率同为 100%。
2. **形态 ② `trimmed`（按来源裁剪）不采用**：虽然 prompt token 省 10.5%，
   但**输出反而更长**（+13.3%）、耗时最高（+8.6%）、强规则通过率掉到 8/9（1 次标题层级超限拦截）、
   lint 警告翻 3 倍。裁剪把「删除清单」类约束一起裁掉了，模型少了明确禁令就写得更啰嗦。
   → 该形态保留在代码里供复测与对照，**生产不启用**。
3. 形态 ③ 还有一个未在本轮量化的潜在优势：同一批次内每一天的 system prompt **完全相同**，
   对支持 prompt 缓存的服务商可命中前缀缓存；① / ② 的规则随日期变化，缓存命中率更低。
4. **P3 顺带修掉两个会拦死写入的真实缺陷**（详见 §5）：`forbid_raw_html` 把
   `` `session:<id>` `` 这类占位符误判为 HTML；`sanitize()` 漏剥推理模型的 `<think>` 思考块。
   修复前，三个形态在真实数据上**全部**被判强规则失败——本次对比在修复后才具备意义。

---

## 二、问题与形态定义

要回答的问题：技能规则的**注入位置与注入量**如何影响成本、耗时、稳定性与合规率。
三形态的「任务 / 目标 / 来源 / 输出要求」措辞**逐字一致**，差异只允许出现在规则块
（有单测 `test_user_prompt_task_section_identical_across_deliveries` 守着），因此结果可归因到形态本身。

| 形态 | 规则放哪 | 注入量 | 现状 |
|---|---|---|---|
| ① `doc_full` | user prompt | 格式化规则摘要 + `style_rules` 全量 + **模板文档全文**（含 frontmatter 规则块与说明正文） | P1 / P2 的行为（对照基线） |
| ② `trimmed` | user prompt | 同上，但按**当日来源类型**裁剪规则，且模板只给**章节骨架**（标题行） | P3 新增，仅用于对比 |
| ③ `system_embedded` | **system prompt** | 与 ① 完全相同的文本，只是换到 system 角色；user prompt 里留一句指引 | P3 新增，**已定为默认** |

### 2.1 形态 ② 的裁剪口径

「按来源裁剪」需要一个可复现的口径，而不是凭感觉删规则。本报告采用**来源语义归类**：
`preset-wlog-daily-std` 的 6 条 `style_rules` 里，只有 2 条是 **B 类（session / 时间戳导出）专属**语义，
其余 4 条跨来源通用；当天没有 B 类来源时不注入那 2 条。

| # | 规则（截断） | 归类 | 判据 |
|---|---|---|---|
| 1 | 保留：明确问题与根因、修复方案与结果、用户做出的选择… | 通用 | 任何来源都可能含这些事实 |
| 2 | 删除：Session Key / Session ID / Source、Conversation info (untrusted metadata) 整段 JSON… | **B 专属** | 这些壳只存在于 session 导出 |
| 3 | 只保留结论，不保留过程：多轮状态轮询、重复的失败重试日志… | 通用 | 过程流水任何来源都可能有 |
| 4 | 改写成客观记录：去掉「喵呜～」「蹭蹭～」等对话腔与过渡语 | **B 专属** | 对话腔来自会话记录 |
| 5 | 默认不做敏感信息脱敏 | 通用 | 策略性约束 |
| 6 | 整理目标是有用而非最短 | 通用 | 策略性约束 |

归类由代码里的文本特征识别实现（`daily_merge_service._B_ONLY_MARKERS`），
因此**没有改动内置预设的 `style_rules` 契约**，用户重排规则顺序也不会失效；
实测归类结果：无 B 来源时注入 4 条，有 B 来源时注入 6 条（含「删除清单」与「对话腔改写」）。

## 三、方法

- **样本集**（刻意覆盖不同来源构成，均为真实 Agent `memory/` 数据）：

| # | Agent | 日期 | 来源构成 | 体积 |
|---|---|---|---|---|
| 1 | `main` | 2026-07-03 | A + B（主骨架 + 一个 session 导出） | 5.9KB + 6.8KB |
| 2 | `main` | 2026-07-14 | B（纯 session 导出，单来源质量差） | 6.2KB |
| 3 | `main` | 2026-07-06 | A + C（主骨架 + 主题文件） | 1.2KB + 2.4KB |

- **重复**：每个 (形态 × 样本日) 连跑 3 次，共 3 × 3 × 3 = **27 次调用**，全部成功（0 失败）。
- **指标**：prompt / completion / total token、单日耗时、强规则通过率、lint 警告数、
  同一样本三次输出的两两相似度（`difflib.SequenceMatcher.ratio`）与 completion 离散度（CV）。
- **护栏**：`--token-budget` 硬中止线（本轮设 400k，实耗 132k）；样本日固定在脚本里；
  只在 `index.db` **副本**上跑，不写 workspace、不改真实库。
- **归并结果不落盘**：`plan_day()` 本身只出计划，因此整轮对比对真实数据零副作用。

## 四、实测结果

### 4.1 成本与耗时（9 次均值）

| 指标 | ① `doc_full` | ② `trimmed` | ③ `system_embedded` |
|---|---|---|---|
| prompt token / 天 | 3,441 | **3,080**（−10.5%） | 3,463（+0.6%） |
| completion token / 天 | 1,551 | 1,757（+13.3%） | **1,400**（−9.7%） |
| total token / 天 | 4,992 | **4,837**（−3.1%） | 4,864（−2.6%） |
| 成本估算 / 天（项目粗估口径：输入 $0.01/M、输出 $0.03/M） | $0.0809 | $0.0835（+3.2%） | **$0.0766**（−5.3%） |
| 单日耗时 | 26.60s | 28.89s（+8.6%） | **23.07s**（−13.3%） |
| 整月耗时外推（132 天，串行） | 58.5 min | 63.6 min | **50.8 min** |

> **为什么看成本而不是总 token**：completion 的单价是 prompt 的 3 倍（项目既有口径
> `_estimate_cost`），所以 ②「省输入但多输出」是净亏，③「输入持平但少输出」是净赚。
> 整轮 27 次调用共 132,238 tokens，项目粗估 $2.17（该口径按 GPT-4o 量级换算，
> 与本轮实际服务商价格无关，只用于形态间横向比较）。

### 4.2 结构与稳定性

| 指标 | ① `doc_full` | ② `trimmed` | ③ `system_embedded` |
|---|---|---|---|
| 强规则通过率 | 9/9 = 100% | **8/9 = 88.9%** | 9/9 = 100% |
| lint 警告 / 次 | 0.11 | 0.33 | 0.11 |
| 三次输出相似度（越高越稳） | 0.442 | 0.393 | **0.518** |
| completion 的 CV（越小越稳） | 0.347 | 0.378 | **0.309** |
| 三次输出完全相同的样本 | 0 | 0 | 0 |

**逐日明细（completion token 三次 / 相似度）**：

| 样本日 | ① | ② | ③ |
|---|---|---|---|
| 2026-07-03 | 1870 / 2034 / 2648（CV 0.153，sim 0.390） | 2291 / 2346 / 3023（CV 0.130，sim 0.300） | 1840 / 2009 / 2023（CV **0.042**，sim **0.471**） |
| 2026-07-14 | 820 / 1422 / 888（CV 0.258，sim 0.335） | 767 / 1184 / 1302（CV 0.212，sim 0.349） | 766 / 901 / 1192（CV 0.187，sim **0.432**） |
| 2026-07-06 | 1335 / 1548 / 1395（CV 0.063，sim 0.601） | 1313 / 1695 / 1895（CV 0.148，sim 0.530） | 1290 / 1290 / 1292（CV **0.001**，sim **0.650**） |

- ③ 在**三个样本日上的一致性全部高于** ①②；2026-07-06 的三次 completion 是 1290 / 1290 / 1292，
  几乎完全重合——规则位于 system 角色时，模型对「写多少」的自由度明显更小。
- ② 的唯一一次失败出现在 A+C 样本日（2026-07-06 第 2 次），共 9 处格式违规，抽样均为
  `FMT-HEADING-LEVEL`（4 级标题超过模板上限 3）：这天没有 B 来源、规则被裁到只剩 4 条，
  模型对结构约束的把握随之变松，写出了 3 层标题。

### 4.3 规则的改动成本

| 动作 | 实测结论 |
|---|---|
| 改预设的 `style_rules` | **下一次调用即生效**（`applied_immediately=true`、`reverted_immediately=true`），无需重启、无需发版 |
| 是否需要重启进程 | **否**（预设存 DB，`PresetService` 每次现读） |
| 是否需要发版 | **否**；只有改代码或改附录 C 的阈值常量才需要发版 |
| 换 LLM provider | 热加载，改完即可用 |

三形态在这一项上没有差别——规则来源都是同一个预设，差别只在「放哪、放多少」。
批次表记录了 `preset_version`，「某个批次用了哪一版规则」永远可追溯。

## 五、实测发现的缺陷（已修，是本次对比的前提）

### 5.1 `forbid_raw_html` 把占位符误判为原始 HTML → 整天无法写入

- **现象**：首轮诊断中三个形态**全部**被判「含原始 HTML」，强规则通过率 0/3。
- **根因**：该规则用 `<([a-zA-Z][a-zA-Z0-9-]*)(\s|/?>)` 匹配，任何 `<单词>` 都算违规。
  而真实日志里合法地存在 `` `session:<id>` ``、`` `cron:<jobId>` ``、`<ID>` 这类枚举取值与占位符
  （常写在行内代码里）。该规则**没有机械修正手段** → 该天直接不能写入。
- **修复**：只认**真实会渲染的 HTML 标签名**（内置标签白名单），并跳过行内代码跨度
  （围栏代码块此前已跳过）。`<br/>` / `<div>` / `<IMG src=a>` / `</span>` 仍会被拦。
- **验证**：把首轮失败的三份输出重新过校验器，`ok=False → ok=True`、违规 0 项。
  回归测试 `test_validate_html_placeholders_not_flagged` / `test_validate_real_html_variants_still_flagged`。
- **影响面**：M15 归并、M13 AI 整理、应用预设共用同一校验器，三者同时受益。

### 5.2 `sanitize()` 漏剥推理模型的思考块

- **现象**：本轮 **27 / 27 次调用**的输出都以 `<think>…</think>` 开头——不是偶发，是这个模型的默认输出形状。
- **根因**：净化逻辑此前只靠中文前言特征词（「让我」「以下是」…）判定思考过程。该模型的思考内容
  **中英文随机**（同一批次里既有 `让我分析这个任务…` 也有 `Let me analyze the task…`）：
  中文的那次能靠特征词侥幸剥掉，英文的那次匹配不上 → `<think>` 残留进正文 → 触发 `forbid_raw_html`，
  把一次成功的归并误判为强规则失败。
  （精确说明：27/27 的 `<think>` 是实测观测；「英文思考块会漏剥并进而触发 HTML 规则」是据此推断的
  因果链——它同时也是「任何只靠中文特征词的启发式都不够用」的充分理由，故直接按标签做了确定性剥离。）
- **修复**：按标签显式剥离（`think` / `thinking` / `reasoning` / `scratchpad` / `analysis`），
  且只在「整段输出以思考块开头」时才剥——正文里作为示例出现的标签不受影响；
  未闭合的块（被 `max_tokens` 截断）不剥，留给强规则如实报错，避免把正文误删。
- **验证**：4 个新增单测；本轮 27 次调用全部正确剥离、强规则通过率回到 100%。

## 六、局限与后续

1. **单 provider / 单模型 / 3 个样本日**。三个样本日上结论方向一致，但样本量不足以做统计显著性判断。
   换模型（尤其是非推理模型）后应重跑对比台复测。
2. **逐日输出不是确定性的**：同一天跑三次的相似度只有 0.39~0.65（措辞与展开程度不同）。
   这不是形态缺陷，而是 LLM 的固有属性——**这正是 M15 必须逐日人工确认、且写入前自动备份的原因**。
   若将来要提高可复现性，可考虑固定 `temperature=0` 或引入「同日二次调用取一致项」的做法（成本翻倍，暂不做）。
3. **未做人工 golden set 比对**：本报告只度量成本 / 耗时 / 稳定性 / 合规率，
   「关键事实保留率 ≥ 95%」属方案 §9.2 的质量验收项，需人工核对，不在本报告范围内。
4. **未验证 prompt 缓存收益**（§1 第 3 条）：需要支持前缀缓存的 provider 才能测。
5. **形态 ② 保留在代码里**供复测对照（`DELIVERIES` 三形态 + `daily_form_bench.py --forms`），
   生产默认只走 ③；若后续评测认为 ② 有价值，只需改 `DEFAULT_DELIVERY` 一个常量。
6. **测量之后 prompt / 预设又改过两处**（本报告的 token 与耗时数字是改动前的基线，方向性结论不受影响）：
   - v1.7 预设收口：`style_rules` 由 6 条 → 7 条（并入归档顺序规则）、必填章节 4 → 5（补「明日计划」）
   - v1.8 空日决策：【输出】段落改为「情形一 / 情形二」两种合法输出，并新增哨兵识别
   这两处都只影响 prompt 的**规则与输出契约**部分，不改变三形态的对比结构；需要精确数字时用 §7 的命令重跑。

## 七、如何复测

```bash
cd backend
# 全量：3 样本 × 3 形态 × 3 次重复（约 27 次真实调用，注意产生费用）
.venv/Scripts/python.exe daily_form_bench.py --repeats 3 --out ../bench-result.json
# 小样本诊断（只跑第 1 个样本日、每形态 1 次）
.venv/Scripts/python.exe daily_form_bench.py --days 1 --repeats 1 --token-budget 60000
# 只测某一形态
.venv/Scripts/python.exe daily_form_bench.py --forms system_embedded
```

脚本会在临时目录复制 `index.db`（含 provider 密钥）后运行，**不动真实库、不写任何 workspace 文件**；
`--token-budget` 越限立即中止。样本日与真实工作量天数（132 天）写在脚本顶部的常量里，改样本只需改那两处。
